# 全局压缩接管：成功验证报告

> **日期**：2026-11-03
> **目标**：接管全局内存压缩（单进程路径已证明不可行）
> **结果**：**成功。双杠杆接管，实测压缩完全停止增长，已恢复原状**

---

## 1. 核心成果

### 1.1 两个真正有效的全局杠杆

| 杠杆 | 地址 | 作用 |
|---|---|---|
| **bit 0x20** | `SM_PARTITION+0x7D0` | 压缩功能使能位（停止接收新页） |
| **节流值** | `SM_COMPRESS_MANAGER+0x28` | 压缩线程优先级/节流（1 最快 ↔ 16 最慢） |

**两者都实测有效，且内核不会自动恢复。**

### 1.2 决定性证据

```
接管前（bit=1，throttle=1）：
  加压 8GB  → 压缩进程 Peak 从 0 涨到 81.1 MB，继续涨到 547.5 MB

接管后（bit=0，throttle=16）：
  Peak before: 547.5 MB
  加压 6GB   → Peak: 547.5 MB
  Peak 增长:   0 MB          ← 完全不增长
```

**这是本轮最强证据：压缩存储彻底停止接收新页。**

## 2. 全局压缩管理器结构（完整解出）

### 2.1 SM_COMPRESS_MANAGER 位置

`SM_PARTITION + 0x4F0`

从 `SmStorePrepare` 调用处确认：
```
0x4EABD9  lea rcx, [rsi + 0x4f0]
0x4EABE3  call SmCompressManagerStart
```

### 2.2 结构布局（实测值）

| 偏移 | 值 | 含义 |
|---|---|---|
| `+0x00` | `0xFFFFD088A5ACE010` | **指回 SM_PARTITION**（`SMKM_STORE_MGR`） |
| `+0x10` | `0xFFFFD088D6AB42F0` | 数组 B |
| `+0x18` | `0xFFFFD088D6CFD5C0` | **SM_COMPRESS_CONTEXT 数组** |
| `+0x28` | `0x1` → `0x10` | **节流值（关键杠杆）** |
| `+0x2C` | `0x1` | 状态 |
| `+0x30` | `0x10001` | 标志 |
| `+0x38` | `0xFFFFFF` | 掩码 |

`SMKM_STORE_MGR[+0x7D4]` = 每节点上下文数 = **1**

`SM_COMPRESS_CONTEXT` 每个 **0x110 字节**

### 2.3 优先级表（`SmStGetPriorityByMemoryCondition`，RVA `0x38018`）

| `SMP_MEMORY_CONDITION` | 压缩线程优先级 |
|---|---|
| 0 | 18 |
| 1 | 18 |
| 2 | 10 |
| 3 | 8 |
| 4 | **-1** |

### 2.4 节流算法（`0x4C00AF`–`0x4C00D6`）

```
cond 0 → 优先级 18 → 节流 ×3
cond 2 → 优先级 10 → 节流 ÷2
cond 3 → 优先级  8 → 节流 ÷4
cond 4 → 优先级 -1 → 节流 ÷8
节流值上限 16，下限 = 每节点上下文数
```

## 3. 完整接管代码路径

```c
// 1. 定位 Memory Compression 进程（EPROCESS 名是 "MemCompr"）
//    必须走 PspCidTable（PsLookupProcessByProcessId），
//    它不挂 ActiveProcessLinks 链表

// 2. 解析 SM_PARTITION
partition = *(UINT64*)(eprocess + 0x758);
smPart    = *(UINT64*)(partition + 0x18);

// 3. 杠杆 1：清 bit 0x20
*(UINT32*)(smPart + 0x7D0) &= ~0x20;      // 0x7B -> 0x5B

// 4. 杠杆 2：调 SmCompressManagerUpdateMemoryCondition(mgr, 4, 1)
mgr = smPart + 0x4F0;
((PFN)(ntBase + 0x4C0040))((PVOID)mgr, 4, 1);
// 结果：节流 1 -> 16，压缩线程优先级 -> -1
```

**`ntBase` 反推方法**（无需硬编码）：
```c
ntBase = *(UINT64*)(&__imp_DbgPrint) - 0x358CB0;   // DbgPrint 的 RVA
```

## 4. 实测数据汇总

### 4.1 杠杆 1（bit 0x20）

| 阶段 | `Flags7d0` | bit 0x20 |
|---|---|---|
| 初始 | `0x7B` | 1 |
| 清除后 | `0x5B` | 0 |
| 2 分钟后复读 | `0x5B` | 0（**持久**） |
| 压力测试后 | `0x5B` | 0（**持久**） |
| 恢复后 | `0x7B` | 1 |

### 4.2 杠杆 2（节流值）

| 阶段 | `Mgr+0x28` |
|---|---|
| 初始 | `1` |
| 设 cond=4 后 | **`16`**（上限） |
| 恢复 cond=0 后 | `3` |

### 4.3 效果对比

| 配置 | 加压时压缩进程 Peak 增长 |
|---|---|
| bit=1, throttle=1 | +81 MB → +547 MB（持续增长） |
| **bit=0, throttle=16** | **+0 MB（完全不涨）** |

## 5. 重要发现：节流 ≠ 开关

单独用节流（`cond=4`）时：

```
节流值 16，加压 8GB → 压缩进程 Peak 68.9 MB
```

**压缩仍在工作**，只是变慢。`UpdateMemoryCondition` 是**油门不是刹车**。

**真正停止压缩必须清 bit 0x20。** 两者组合才是完整接管。

---

## 6. 为什么单进程压缩做不到（承接上一轮）

| 环节 | 状态 |
|---|---|
| `SmpKeyedStoreCreate` | ✅ 调用成功（`STATUS_SUCCESS`） |
| `SmFirstTimeInit` 门禁 | ❌ 要求 `SM_PARTITION+0x838` 非 0 |
| `F838` 语义 | ❌ 是 `PsCreateMinimalProcess` 的**父进程指针**，不是占位符 |
| 当前值 | `0`（系统从未配置） |
| 结论 | **per-process store 在当前配置下内核不开放** |

## 9. 结论

**全局压缩接管成功，且可逆。**

两个杠杆组合可以完全压制内存压缩：
1. **清 bit 0x20** → 停止接收新页（决定性）
2. **调 cond=4** → 压缩线程优先级降到 -1，节流 16（辅助）

实测加压 6 GB，压缩存储 Peak **零增长**。

**限制**：这只阻止**新的**压缩，已压缩的数据不会立即释放（需要 `SmFeEvictInitiate` 驱逐，涉及 B+ 树操作，风险高）。
