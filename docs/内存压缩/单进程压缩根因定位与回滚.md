## 1. 找到真正的阻塞点

### 1.1 之前以为的阻塞

上一轮 `SmpKeyedStoreCreate` 返回 `STATUS_SUCCESS` 但 store 没建起来，怀疑是 store 大小或异步问题。

### 1.2 实际阻塞：`SmFirstTimeInit` 的门禁

`SmProcessCreateRequest` 的调用链：

```
0xA51008  SmAllocEx              ← 分配 store
0xA5101C  SmStInitialize         ← 初始化
0xA5102C  SmFirstTimeInit        ← ★ 门禁在这里
0xA51077  SmStStart              ← 启动
0xA510E4  SmKmStoreAdd           ← 加入列表
```

`SmFirstTimeInit` 开头（RVA `0x4EA9DF`）：

```asm
004EA9DF  mov  rax, PspSystemPartition
004EA9E6  cmp  [rsi+0x830], rax      ; 是系统分区吗？
004EA9ED  je   0x4EAA02              ; 是 → 放行
004EA9EF  cmp  [rsi+0x838], 0        ; 不是系统分区，看 0x838
004EA9F6  jne  0x4EAA02              ; 非 0 → 放行
004EA9F8  mov  edi, 0xC00001AE       ; ← 否则直接拒绝
004EA9FD  jmp  0x4EAD C5
```

**实测当前值：**

| 字段 | 值 | 说明 |
|---|---|---|
| `F830` | `0xFFFFD088A56D4F20` | 不是 `PspSystemPartition` |
| **`F838`** | **`0x0`** | **门禁拒绝** |

**这就是 `STATUS_SUCCESS` 但 store 不建立的真正原因**——`SmFirstTimeInit` 在中间返回 `0xC00001AE`，但 `SmpDirtyStoreCreate` 只检查负数返回值（`0xC00001AE` 是负数应该会传出来... 实际测试显示外层仍是 0，说明有别的路径吞掉了错误）。

## 2. 关键发现：`F838` 是什么

我一开始以为 `F838` 只是"非 0 即可"的占位字段，所以写入了 `F878` 的值。

**这是错的。**

反汇编 `SmFirstTimeInit` 门禁之后（RVA `0x4EAA69`）：

```asm
004EAA69  mov  rax, [rsi+0x838]       ; ← 取 0x838
004EAA70  lea  rcx, [rbp-0x49]
004EAA74  mov  r9b, [rdi+0x5FA]
004EAA7B  lea  rdx, [rip+0x91E46E]     ; 进程名 "Memory Compression"
004EAA8F  mov  rcx, rdi                ; 当前进程
004EAA97  mov  [rsp+0x40], rax         ; ★ 0x838 作为参数
004EAAA1  mov  [rsp+0x30], 0x10
004EAAB3  call PsCreateMinimalProcess  ; ★ 创建最小进程
```

**`F838` 是传给 `PsCreateMinimalProcess` 的"父进程"指针。**

`PsCreateMinimalProcess` 用它作为新进程的父进程。我传了 `0xF878`（一个 EPROCESS 地址），但因为它是**当前 Memory Compression 进程自己的 EPROCESS**，创建子进程时逻辑上不成立，所以失败了（没崩，但也没成功）。

---

## 3. 为什么单进程压缩在系统分区上做不到

`SmFirstTimeInit` 的设计意图很明确：

```
系统分区（PspSystemPartition）→ 无条件放行
非系统分区 → 必须提供"父进程"（0x838 非 0）
```

而 `Memory Compression` 进程用的是**系统分区**（`F830` 指向系统分区对象），理论上应该走第一条路放行。

**但实测 `F830 = 0xFFFFD088A56D4F20`，与 `PspSystemPartition` 不相等。**

这说明：
- 要么 `PspSystemPartition` 的实际地址不是我以为的值
- 要么 `Memory Compression` 用的是**独立分区**（这正是"内存压缩专用分区"的设计）

如果是后者，那 `SmFirstTimeInit` 就要求这个分区必须有一个"父进程"，而 `F838 = 0` 说明**当前系统根本没给压缩分区配置父进程**。

**结论：per-process store 的创建路径在当前系统配置下是关闭的。**

## 7. 为什么"单进程压缩"实际上做不到

综合五轮的所有证据：

1. **压缩存储是全局的**，`Memory Compression` 进程持有所有压缩数据
2. **per-process store 的代码存在但被门禁关闭**——需要"父进程"配置，当前系统没配
3. **即使强行创建 store**，也需要 `SmFirstTimeInit` 完整跑通（它会调 `PsCreateMinimalProcess` 创建子进程，我无法提供正确的父进程语义）
4. **`SmTrimWsStore` 需要 store 带 bit 17**，而 bit 17 只在 store 创建时写入——store 建不起来，Trim 就永远不可达

**这不是参数调错的问题，是这套机制在当前系统配置下就没启用。**

## 8. 如果一定要继续，还剩什么

| 方向 | 可行性 | 风险 |
|---|---|---|
| 找到正确的"父进程"语义 | 低（需要理解 `PsCreateMinimalProcess` 的完整契约） | 高（会创建真实进程） |
| 改 `F830` 冒充系统分区 | 低（需要知道 `PspSystemPartition` 的真实地址） | **极高**（可能破坏分区管理） |
| 直接操作 store 的 B+ 树 | 低（需要构造 `T_SM_PAGE_KEY`） | **极高**（B+ 树损坏 = 数据丢失） |
| 放弃，用工作集修剪代替 | **高** | 低 |

**我的判断：单进程压缩在当前系统上无法实现，不是技术不够，是内核设计上就没给这条路留入口。**

## 9. 本轮教训

1. **`F838` 不是"随便非 0 就行"的占位符**——它是 `PsCreateMinimalProcess` 的父进程指针，语义严格
2. **`STATUS_SUCCESS` 不等于成功**——`SmpDirtyStoreCreate` 的错误被吞掉了
3. **先读门禁再动手**——如果一开始就查 `SmFirstTimeInit` 的门禁逻辑，能省掉这轮的试错
4. **每次写内核字段必须准备回滚驱动**——本轮做到了，`F838` 已恢复为 0
