# 主动压缩与无压力压缩：技术分析报告

> **日期**：2026-11-03
> **你的两个需求**：
> 1. 制造内存压力时，让内存压缩优先级保持高
> 2. 无压力时也能主动压缩，回收"死内存"（像 Linux 那样）
>
> **结论**：需求 1 可行且已验证；需求 2 的接口存在，但被**作用域限制**卡住

---

## 1. 先回答你的第一个问题：之前从没主动压缩过

**六轮实验做的全是"抑制"**：

| 动作 | 性质 |
|---|---|
| `Disable-MMAgent` | 关 |
| 清 `[+0x7D0]` bit 0x20 | 关 |
| 调 `UpdateMemoryCondition(4)` | 降速 |
| 改 `[+0x838]` | 尝试建 store（失败） |

**一次主动触发压缩都没有。** 这是真实的盲区。

## 2. 需求 1：有压力时保持高优先级 —— ✅ 可行

### 2.1 当前实测状态

```
Flags7d0   = 0x7B    (bit 0x20 = 1，压缩已启用)
MgrThrottle = 1      (节流值 1 = 压缩最快)
StoreFlags = 0x320800 (bit 17 = 1)
```

**系统当前就是"最高优先级"状态。** 默认配置下压缩线程优先级 18（高于常规）。

### 2.2 如何保持高优先级

调 `SmCompressManagerUpdateMemoryCondition(mgr, cond, flag)`，`cond=0` 或 `1`：

| cond | 优先级 | 节流 |
|---|---|---|
| 0 | 18 | ×3 → 上限 16 |
| 1 | 18 | ×3 |
| 2 | 10 | ÷2 |
| 3 | 8 | ÷4 |
| 4 | **-1** | ÷8 |

**已验证可调用**（第 6 轮）：
```
ThrottleBefore = 16  →  调 cond=0  →  ThrottleAfter = 3
ReturnStatus   = 7
```

**结论：需求 1 完全可行，且不需要改内核内存——这是官方接口。**

## 3. 需求 2：无压力主动压缩 —— 接口存在，但被作用域卡住

### 3.1 目标接口：`SmProcessSystemStoreTrimRequest`

```
NtSetSystemInformation(0x6D, sub=0x14) → SmProcessSystemStoreTrimRequest
  → SmKmStoreGet(分区, store索引)
  → SmTrimWsStore(分区, store, 参数)
  → SmStTrimWsStore(store, 参数)
  → SmStMapVirtualRegion + SmStTrimWsStoreBatch
```

### 3.2 关键发现：store 的 bit 17 **已经是 1**

```
StoreIndex = 0x400
StoreObj   = 0xFFFFD088DB3F0000
StoreFlags = 0x320800
Bit17      = 1              ← 门槛已满足！
```

**上一轮我以为 `SmTrimWsStore` 因 bit17 未设而不可达，这个判断是错的。**

### 3.3 真正的阻塞：API 只作用于调用者自己所在的分区

`SmProcessSystemStoreTrimRequest` 的核心（RVA `0xA78605`）：

```asm
004A78605  mov  rax, gs:[0x188]        ; 当前线程
004A7860E  mov  rcx, [rax + 0xB8]      ; 当前进程 EPROCESS
004A78615  call SmpGetProcessPartition ; ← 取【当前进程】的分区
004A7861A  mov  rbx, rax               ; rbx = SM_PARTITION
004A78743  mov  edx, [rbx + 0x8E0]     ; 该分区的 store 索引
```

**`SmpGetProcessPartition` 用 `gs:[0x188]` 取当前进程，不接受外部指定进程。**

### 3.4 为什么这导致失败

我的 PowerShell 进程在**默认分区**，该分区：
- `[分区+0x8E0]` 的 store 索引指向的不是压缩 store
- 即使有 store，也不是 `Memory Compression` 那个带 bit17 的 store

所以 `SmTrimWsStore` 拿到的 store 没有 bit17 → 返回 `0xC00000BB`。

**这不是参数问题，是 API 的作用域限制。**

### 3.5 实测证据

```
flags=1 (bit8=0) val8=1/4096/1048576/1GB  →  全部 0xC00000BB
flags=0x101 (bit8=1) val8=1/4096          →  全部 0xC0000008
```

无论怎么调参数都是 `NOT_SUPPORTED`，因为**分区不对**。

---

## 4. 解决方案

### 4.1 需求 1 的实现（简单）

```c
// 驱动里：
mgr = smPart + 0x4F0;
((PFN)(ntBase + 0x4C0040))((PVOID)mgr, 0, 1);   // cond=0 → 优先级 18
```

**已验证，无需改内存。**

### 4.2 需求 2 的实现（需要两步）

**方法 A：在压缩进程上下文里调用**（推荐）

驱动需要：
1. 定位 `Memory Compression` 进程的 EPROCESS
2. `KeStackAttachProcess(eprocess)` 切换上下文
3. 调用 `NtSetSystemInformation(0x6D, sub=0x14, ...)`
4. `KeUnstackDetachProcess`

这样 `gs:[0x188]` 就指向压缩进程，`SmpGetProcessPartition` 返回正确分区。

**方法 B：直接调用内部函数**（绕过 API）

```c
// 直接调 SmTrimWsStore，跳过 SmProcessSystemStoreTrimRequest
store = [arr + lo*0x28];          // 单层解引用
((PFN)(ntBase + 0x4BEB1C))((PVOID)smPart, (PVOID)store, param);
```

这样不需要切上下文，但需要知道 `param` 的正确值。

## 5. 关键偏移修正记录

本轮发现上一轮的一个**解引用错误**：

```c
// 错误（少一层）
store = *(UINT64*)(arr + lo*0x28);

// 正确（SmKmStoreGet 的 0x349F46 处 rax = [rax]）
store = *(UINT64*)(arr + lo*0x28);   // 单层，返回 0xFFFFD088DB3F0000
```

**实际验证：单层解引用得到 `0xFFFFD088DB3F0000`，其 `[0]=0x320800`，bit17=1，是正确的 store。**

如果多解一层会得到 `0x8000320800`（垃圾值）。

**结论：单层解引用是对的。**
