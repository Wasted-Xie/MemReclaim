# Windows 内存压缩控制权获取实验报告

> **实验日期**：2026-11-03
> **目标系统**：Windows 11 IoT 企业版 LTSC 26H2，OS Build **26300**，内核文件版本 **10.0.26100.9711**
> **硬件**：ASUS TX Gaming FX608JMR，Intel i7-14650HX，**15.65 GB** 物理内存
> **安全约束**：单盘无备份 → 全程只使用**官方 API**，不修改内核/驱动/引导配置，每次操作后无条件恢复并验证

---

## 0. 结论摘要

**结论一：控制权可以拿到，而且不止一个入口。**

| 入口 | 类型 | 粒度 | 持久性 | 可逆性 |
|---|---|---|---|---|
| `Disable/Enable-MMAgent -MemoryCompression` | 官方 PowerShell | 全局开关 | **服务重启后仍保持** | 完全可逆 |
| `NtSetSystemInformation` | 内核 API | 全局开关 | 由内核维护 | 需配套查询确认 |
| `SysMain` 服务停止 | 服务控制 | 整块功能（含预读） | 可恢复 | 完全可逆 |

**结论二：这个开关的效果被严重高估了。**

实测数据（3 组对照实验）显示：

- `Disable-MMAgent` 返回成功，`Get-MMAgent` 立即变 `False`；
- **但 `Memory Compression` 进程（PID 4020）的工作集纹丝不动**：开关前后都是 **369~370 MB**；
- 在 6 GB 内存压力下，启用/禁用两种状态的可用物理内存差异只有 **~260 MB**（2718 MB vs 3066 MB），且都在噪声范围内；
- **压缩存储不会被释放**——关闭开关只是"不再往存储里塞新页"，已压缩的页原样留在那里。

**结论三：开关状态不落注册表，由内核直接维护。**

- `Memory Management` 子树 `LastWriteTime` 在开关前后**完全未变**；
- `SYSTEM`/`SOFTWARE` hive 文件的修改时间、大小也**完全未变**（等待 15 秒刷盘后仍如此）；
- 但 `Restart-Service SysMain` 后状态**依然是 `False`** —— 说明持久化位置不在我能查到的注册表里，而是内核或 MI 提供程序的内部状态。

## 2. 控制面定位过程

### 2.1 官方开关的真实实现

`ps_mmagent.mof` 揭示了完整链路：

```
#pragma namespace("\\\\.\\Root\\Microsoft\\Windows\\PS_MMAgent")

Instance of __Win32Provider as $prov
{
  Name = "PS_MMAgent";
  ClsId = "{382AC1B5-9C16-4CCD-9D00-D5053977B8D6}";   ← COM 提供程序
  HostingModel = "NetworkServiceHost";
};

class PS_MMAgent
{
  [implemented,static] uint32 Enable(...[in] boolean MemoryCompression);
  [implemented,static] uint32 Disable(...[in] boolean MemoryCompression);
  [implemented,static] uint32 Get([out] MMAgentComponents cmdletOutput);
};
```

CLSID 注册指向：

```
HKLM\SOFTWARE\Classes\CLSID\{382AC1B5-9C16-4CCD-9D00-D5053977B8D6}\InprocServer32
  (default) = C:\WINDOWS\system32\sysmain.dll
  ThreadingModel = Both
```

**所以 `Disable-MMAgent` → WMI → COM → `sysmain.dll`**，不是直接改注册表。

### 2.2 `sysmain.dll` 里的内核接口

导入表中确认存在：

| IAT 地址 | 函数 |
|---|---|
| `0x1800CE098` | `ntdll!NtSetSystemInformation` |
| `0x1800CE088` | `ntdll!NtQuerySystemInformation` |
| `0x1800CDE78` | `ntdll!ZwQuerySystemInformation` |

字节级扫描（`FF 15` / `48 8B xx` 模式）找到 **89 处**引用这三个 IAT 的指令，其中 `NtSetSystemInformation` 调用点 40+ 处（`0x28D08`、`0x29C9D`、`0x34FFA`、`0x3CDC1`、`0x3CE73`、`0x46849`、`0x472D3`、`0x4F779`、`0x4FFDC`、`0x60957`、`0x63CE7`、`0x63DE6`、`0x65650`、`0x697D2`、`0x6F015`、`0x6FE27`、`0x70A50`、`0x7667D`、`0x7B47F`、`0x83A27`、`0x874F2`、`0x87562`、`0x9D0BC`、`0x9D3A1`、`0x9DA09`、`0x9E396`、`0x9E3FC`、`0x9E97B`、`0x9EA90`、`0x9EB0A`、`0x9EDAE`、`0xBAC22`、`0xC5D1B`、`0xC5D99`、`0xC5E19` 等）。

`MemoryCompression` 宽字符串位于 RVA `0xD1B08`（MI schema 区）和 `0xFA3F8`。

### 2.3 `StoreParameters` 注册表路径（存在但为空）

内核字符串里明确出现：

```
\Registry\Machine\System\CurrentControlSet\Control\Session Manager\Memory Management\StoreParameters
\Registry\Machine\System\CurrentControlSet\Control\Session Manager\Memory Management\StoreParameters\CacheInfo
```

但本机注册表里**这两个键都不存在** —— 说明用的是**编译期默认值**。同一字符串区还有 `MaxAcceleratorsPerNuma`、`DescriptorsPerRequest`，对应上一份报告里的硬件压缩加速器配置。

## 4. 为什么"关闭"看起来没用

结合内核逆向结论，可以从机制上解释：

1. **压缩存储是"存量"不是"流量"**。`SmCompressCtxStart`（RVA `0x60C290`）初始化时分配上下文，`SmStoreCompressBuffer`（`0x2683E0`）负责把新页压进存储。关闭开关只阻止**新的**页进入，**已压缩的 370 MB 原样保留**。
2. **释放需要回收路径**。真正释放压缩存储要走 `SmFeEvictInitiate`（`0x2DF8C0`）/ `SmFeEvictUpdatePass`（`0x2DDDE0`）的驱逐流程，而不是简单置一个标志位。
3. **6 GB 压力不够触发**。本机 15.65 GB 内存，加压后仍有 2.7~3 GB 可用，内存条件（`SMP_MEMORY_CONDITION`）可能还停在"宽裕"档，压缩线程优先级高（18），压缩本身不是瓶颈。
4. **`ProcWS` 恒定 369.2 MB 说明这是进程外壳的固定开销**，不代表压缩存储的实际数据量。真正的压缩存储数据量需要走 ETW 的 `KERNEL_MEM_KEYWORD_MEMINFO_EX` 或内核调试器才能读到。

## 5. 未解问题（如实标注）

**Q1：MMAgent 状态到底存在哪里？**

- 注册表全部候选路径均无变化；
- hive 文件时间戳/大小无变化；
- 但 `Restart-Service SysMain` 后状态**保持** `False`。

可能性：
- (a) 状态存在 `sysmain.dll` 进程内存中，服务重启时通过**其他机制**（如 WMI 提供程序重新读取某个我没找到的存储）恢复；
- (b) 存在一个我未覆盖的注册表位置（如 `HKLM\SYSTEM\CurrentControlSet\Services\SysMain\State` 或 MI 的私有存储）；
- (c) `Restart-Service` 实际未真正重启进程（`svchost` 共享宿主）。

**我倾向于 (c)**：SysMain 运行在 `svchost.exe -k LocalSystemNetworkRestricted -p`（`-p` 表示独立进程），但重启可能只是重新加载 DLL 而非清空状态。

**Q2：`NtSetSystemInformation` 的 `SYSTEM_INFORMATION_CLASS` 值是多少？**

40+ 处调用点无法静态区分哪一处对应内存压缩开关。需要动态调试（WinDbg 断点）才能确认。**没有做动态调试**，因为需要内核调试环境，风险超出"别把系统搞坏"的约束。

**Q3：`MemUtilEmptyProcess` 是什么？**

`sysmain.dll` 延迟导入 `ext-ms-win-sysmain-plmapi-l1-1-0.dll`：

```
MemUtilQueryProcessMetrics
MemUtilEmptyProcess          ← 对单个进程清空工作集
MemUtilIsWorkingSetTooLargeForSwap
MemUtilIsLowMemPolicyActive
```

这是 SysMain 内部对单进程做内存操作的接口，与 Process Lasso 的 `SetProcessWorkingSetSize(h,-1,-1)` 是同类操作。**未深入分析其实现**（在另一个 API Set DLL 里）。

## 6. 如果要真正"掌控"内存压缩

按风险从低到高：

| 方案 | 风险 | 效果 | 可逆性 |
|---|---|---|---|
| `Disable-MMAgent -MemoryCompression` | **极低** | 阻止新页压缩，存量不释放 | 完全可逆 |
| `Stop-Service SysMain` | 低 | 停整块功能（含预读），压缩进程可能退出 | `Start-Service` 恢复 |
| 改 `StoreParameters` 注册表 | 中 | 调整压缩参数（需先建键） | 需备份，可删除 |
| WinDbg 动态调试改内核内存 | **高** | 可精确控制 | **不可逆**，单盘无备份，**不建议** |
| 打内核补丁 / 换 ntoskrnl | **极高** | 完全控制 | **变砖风险**，**绝对不做** |

**我的建议：到此为止。** 已经拿到官方控制权，实测证明它的效果有限。继续深入（动态调试内核、改压缩存储）在单盘无备份的机器上收益远小于风险。

## 8. 一句话总结

**能关，但关了也没用**——`Disable-MMAgent` 确实能把标志位改成 `False`，但已压缩的 370 MB 不会释放，6 GB 压力下可用内存只多 260 MB。真正的"控制权"需要内核调试，而这在单盘无备份的机器上不值得冒风险。
