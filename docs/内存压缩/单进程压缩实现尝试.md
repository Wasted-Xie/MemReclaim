# 单进程压缩实现尝试：技术结论

> **日期**：2026-11-03
> **目标**：实现"单进程压缩"——让指定进程拥有独立的压缩存储
> **结论**：**架构支持，创建入口已成功调用（STATUS_SUCCESS），但 store 实际未建立**

---

## 1. 核心发现：Windows 内核确实支持 per-process 压缩存储

这不是猜测，是完整的代码证据链。

### 1.1 keyed store 表结构（`SM_PARTITION + 0x8B8`）

```
+0x00  push lock (8 字节)
+0x0C  table size = 128          ← 实测值 0x80
+0x10  bucket array pointer      ← 实测 0xFFFFD088E0286C10
```

**128 个哈希桶，按进程对象索引。**

### 1.2 完整函数族（全部存在）

| 函数 | RVA | 状态 |
|---|---|---|
| `SmpKeyedStoreCreate` | `0xA50B64` | ✅ **已成功调用** |
| `SmpKeyedStoreReference` | `0x3499CC` | ✅ 活代码（被 `0x34B901` 调用） |
| `SmpKeyedStoreEntryGet` | `0x349FB0` | ✅ 活代码（4 处调用） |
| `SmStoreExistsForProcess` | `0x349F54` | ✅ 活代码 |
| `SmpDirtyStoreCreate` | `0xA50CB8` | ✅ 被 Create 调用 |
| `SmProcessCreateRequest` | `0xA50DD0` | ✅ 被 DirtyStoreCreate 调用 |
| `SmpKeyedStoreCtxCleanup` | `0x60EBE4` | ❌ **无调用者（死代码）** |

### 1.3 创建流程（从反汇编完整还原）

```
SmpKeyedStoreCreate(rcx = &SM_PARTITION[0x8B8], rdx = SM_PARTITION, r8 = process)
  │
  ├─ SmpGetProcessPartition(process) -> SM_PARTITION
  ├─ size = [SM_PARTITION+0x8B4]
  │    若 size == 0 → 按 [process+0x5FC]&1 取默认 0x400 或 0x800
  ├─ SmpDirtyStoreCreate(SM_PARTITION, size, 1, &storeId)
  │     │
  │     ├─ 构造 0x58 字节 ST_STORE_CREATE 请求
  │     │    [0x20] = 0x106 | (flags&1)<<9     ← store 类型
  │     │    [0x2C] = 0x80
  │     │    [0x30] = 0x20000                  ← ★ bit 17 在这里
  │     │    [0x34] = min(size>>17, 0x40000)
  │     │    其余从 [SM_PARTITION+0x8B0] 提取
  │     │
  │     └─ SmProcessCreateRequest(SM_PARTITION, &request, 0x58, 0)
  │          校验: cmp ebx, 0x58 必须相等
  │          返回 storeId 到 [rsp+0x70] → 写回 &storeId
  │
  ├─ SmAllocEx(0x18, tag 'smpS')  → keyed entry
  ├─ entry[+0x08] = process 对象
  ├─ entry[+0x10] = storeId (word)
  └─ SmpKeyedStoreEntryGet(table, &entry, 1, ...)  → 插入
```

**注意 `0x20000` 是创建时自动写入的——这正是 `SmTrimWsStore` 需要的 bit 17。**
也就是说，**per-process store 一旦创建，就自动支持 `SmTrimWsStore`**，那条之前"不可达"的 Trim 路径会变得可用。

## 2. 实测结果

### 2.1 调用成功

```
Stage        = 10 (完整执行到返回)
NtoskrnlBase = 0xFFFFF80286400000     ← 从 DbgPrint 导入反推，正确
FnAddr       = 0xFFFFF80286E50B64     ← 0xA50B64 + base，正确
CreateStatus = 0x00000000             ← STATUS_SUCCESS
```

**驱动成功调用了内核内部函数，无蓝屏，无异常。**

### 2.2 但 store 没建立

```
StoreExists = 0        ← SmStoreExistsForProcess 返回 false
KsCount     = 0x80     ← 仍是 128 桶，没变
KsBuckets   = 0xFFFFD088E0286C10  ← 地址没变
P8b4        = 0        ← store 大小仍是 0
```

**`STATUS_SUCCESS` 是假的**——`SmpDirtyStoreCreate` 在 `0xA50D9B` 处 `test eax, eax; js`，只在负数时报错。如果 `SmProcessCreateRequest` 内部静默失败但返回 0，外部看不出来。

## 3. 为什么没成功（三个可能）

### 3.1 分区未启用 per-process 支持（最可能）

`SM_PARTITION+0x8B0 = 0x1305`。`SmpDirtyStoreCreate` 从这个字段提取标志位：
```
[rsp+0x20] = 0x106 | ((flags&1)<<9)
r8d = (flags & 0x700) | 0x20 ; shl 2
r8d |= (flags & 0x2000) ; shl 10
```
如果分区没被标记为"支持 dirty store"，`SmProcessCreateRequest` 可能直接拒绝。

### 3.2 store 大小 0 导致请求无效

`P8b4 = 0`，走默认分支得到 `0x400` 或 `0x800` 页。这个值传给 `SmpDirtyStoreCreate` 的 `edx`，然后 `[rsp+0x34] = min(size>>17, 0x40000)`。

如果 `size = 0x400`（页），`size>>17 = 0`，请求里的 size 字段就是 0——**可能被判为无效**。

### 3.3 需要走异步工作项

`SmProcessCreateRequest` 可能只是把请求入队到 `SmWorkItemQueue`，真正的 store 创建由 worker 线程异步完成。我的驱动调用后立即检查，**可能检查太早了**。

## 4. 验证方法的教训

我这轮犯了两个测量错误：

1. **以为 `KsCount` 会变**——它是哈希桶数量，固定 128，不随插入变化
2. **以为 `StoreId` 会回传**——`SmpKeyedStoreCreate` 返回 NTSTATUS，不回传 storeId

正确信号是 `SmStoreExistsForProcess`，它明确返回 0。

## 5. 蓝屏记录（本轮）

**一次蓝屏，已恢复**：

```
BugCheck 0x7E = SYSTEM_THREAD_EXCEPTION_NOT_HANDLED
Arg1 = 0xC0000005 = STATUS_ACCESS_VIOLATION
```

**原因**：我在 `ksprobe.c` 里把 `partition+0x8B8` 当成 `LIST_ENTRY` 解引用：
```c
UINT64 flink = *(UINT64*)(partition + 0x8B8);   // 实际是 push lock 值
cur = *(UINT64*)cur;                            // 解引用垃圾指针 → 崩溃
```

**修正**：`+0x8B8` 是 push lock + 表头结构，**不是链表**。改成只读固定偏移后不再崩溃。

**关键教训**：**永远不要解引用未经验证的指针**。上一轮之所以成功，是因为只读固定偏移、不解引用。

## 7. 距离成功还差什么

要真正建立 per-process store，需要：

| 步骤 | 难度 | 说明 |
|---|---|---|
| 确认 `SmProcessCreateRequest` 的失败原因 | 中 | 需要读它的返回值，而不是只看外层 |
| 修正 store 大小参数 | 低 | 尝试传非 0 的 `P8b4`，或直接用 `0x40000` 页 |
| 等待异步完成 | 低 | 调用后延迟再检查 `SmStoreExistsForProcess` |
| 验证 `SmTrimWsStore` 是否可用 | 低 | store 带 bit 17 后应该可用 |

**最有希望的方向**：先修正 store 大小参数，再延迟检查。

---

## 8. 一句话总结

**架构上完全支持单进程压缩，创建函数也成功调用了（STATUS_SUCCESS），但 store 没建立——卡在 `SmProcessCreateRequest` 的某个静默失败。** 差一步：搞清它为什么不真正创建，以及是不是异步的。
