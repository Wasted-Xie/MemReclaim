# 实测数据

本文汇总 MemReclaim 的全部实测记录。README 只保留结论，具体数据、复现条件与
原始输出放在这里，便于核对与复现。

> 测试机：Windows 11 26300（Win11 26H2），x64，16 GB 内存。
> 除特别说明外，测试时程序以管理员权限运行，程序文件位于普通目录（无完整性标签）。

---

## 1. 四项清理功能

普通会话（管理员权限）下逐项实测：

| 清理项 | 实测结果 |
|---|---|
| 待机列表 Standby list | **可用**（曾一次回收 904 MB） |
| 待机列表（无优先级） | **可用** |
| 系统文件缓存 System file cache | **可用** |
| 合并内存列表 Combine | **可用**（曾一次合并 82,885 页） |

两项所需特权均能正常启用：

```
SeProfileSingleProcessPrivilege → 已启用 (RtlAdjustPrivilege)
SeIncreaseQuotaPrivilege        → 已启用 (RtlAdjustPrivilege)
```

合并的典型输出示例：「已合并 13169 页，折算 51.4 MB」。

## 2. 程序文件的完整性标签

实测确认：四项清理能否工作，**取决于程序文件的完整性标签**，而非账户权限。

| 文件状态 | 进程完整性级别 | 四项清理 |
|---|---|---|
| 无标签（普通位置） | `High` | **全部成功** |
| 带 Low 标签（沙箱 / 受管目录） | `Low` | **全部失败** |

检查方法（在程序目录执行）：

```powershell
icacls MemReclaim.exe | Select-String "Mandatory Label"
```

出现 `Mandatory Label\Low Mandatory Level` 即为受限。

### 2.1 复制 vs 移动

NTFS 的规则决定了两种操作结果完全不同：

| 操作 | 机制 | 结果 |
|---|---|---|
| **复制** | 创建新文件，继承目标目录属性 | 标签消失 → **可用** |
| **移动** | 同卷移动＝重命名，ACL 与标签原样保留 | 标签跟着走 → **仍然失败** |

所以正确做法是「右键 → 复制 → 粘贴到普通目录（如 `C:\MemReclaim\`）」，再以管理员身份运行。

> 用 `icacls /setintegritylevel` 强行改标签会被 HIPS 类软件拦截，不要尝试。

## 3. 进程分类分布

本机同一时刻、202 个进程的分类结果，与任务管理器对照：

| 分类 | 数量 | 任务管理器对照 |
|---|---|---|
| 前台应用 | 19 个进程 / **6 个应用组** | 应用 **(6)** |
| 后台应用 | 69 | 后台进程 (79) |
| Windows 进程 | 112 | Windows 进程（截图中未展开） |

差异来自口径：任务管理器的「后台进程」包含 UWP 应用，本工具按有无窗口把它们
归入前台/后台，并按映像路径把多进程应用归组（如 QQ 的 8 个进程算作 1 个应用组）。

## 4. 并发修剪的线程数与耗时

本机 198–203 个进程，其中 12 个为修剪目标：

| 线程数 | 耗时 | 回收量 |
|---|---|---|
| 1 | 11 ms | 24.9 MB |
| 4 | 6 ms | 24.9 MB |
| 8 | 3 ms | 24.9 MB |
| 16 | 2 ms | 24.8 MB |

回收量在各线程数下保持一致，说明并发没有漏处理，只是缩短了墙钟时间。

---

## 5. 工作集修剪的整体效果

本机（16 GB，203 个进程）启用「自动纳入后台应用」后：

```
工作集修剪：171/174 个进程成功，释放约 3.21 GB，耗时 255 ms
```

失败 3 个均为受保护进程（无权限打开句柄），属预期。

> 「释放」指的是本次把多少物理页推出了工作集。进程随后会按需重新调入，
> 所以这是**回收量**而非永久节省量。

### 5.1 效果的时间尺度

`EmptyWorkingSet` 引发的压缩效果约 **6 秒达峰**，**100 秒内消散**。
因此定时高频修剪的净收益接近于零——这正是默认门槛 85%、冷却 600 秒的原因。

## 7. 驱动层主动压缩的尝试

「能不能主动触发内存压缩」这个问题做过一轮完整的逆向与实验，结论与逐项数据见：

- [单进程压缩完整报告.md](单进程压缩完整报告.md)
- [内存压缩触发机制研究.md](内存压缩触发机制研究.md)

要点：驱动层的压缩控制手段（per-process store、主动 Trim、页驱逐、唤醒写入器）
全部零效果；唯一真正触发压缩的是制造真实的「页面需要换出」需求，也就是
`EmptyWorkingSet`（38 个后台进程回收 1,694.8 MB，压缩进程工作集 590 MB → 839 MB）。
