# 单进程内存压缩：完整原理与调用方式

> **日期**：2026-11-04
> **内核**：Windows NT 10.0.26300（Build 26300，内核 10.0.26100.9711）
> **平台**：x64，ASUS TX Gaming FX608JMR，i7-14650HX，15.65 GB RAM
> **状态**：**架构支持，门禁关闭，当前系统无法启用**

本文合并了 2026-11-03 与 2026-11-04 两轮实验的全部实测数据，并修正了早期报告中三处错误结论。

---

## 一、结论先行

### 1.1 单进程压缩在技术上是什么

Windows 内核的压缩存储（SMKM）支持 **per-process store**：为指定进程创建独立的压缩存储，与全局压缩存储并列。

代码证据完整：

| 组件 | 符号 | RVA | 状态 |
|---|---|---|---|
| keyed store 表 | `SM_PARTITION + 0x8B8` | — | 128 个哈希桶，按进程对象索引 |
| 创建入口 | `SmpKeyedStoreCreate` | `0xA50B64` | 可调用，返回 `STATUS_SUCCESS` |
| 引用查找 | `SmpKeyedStoreReference` | `0x3499CC` | 活代码（`0x34B901` 调用） |
| 条目获取 | `SmpKeyedStoreEntryGet` | `0x349FB0` | 活代码（4 处调用） |
| 存在性检查 | `SmStoreExistsForProcess` | `0x349F54` | 活代码 |
| 脏 store 创建 | `SmpDirtyStoreCreate` | `0xA50CB8` | 被 Create 调用 |
| 创建请求 | `SmProcessCreateRequest` | `0xA50DD0` | 被 DirtyStoreCreate 调用 |
| 上下文清理 | `SmpKeyedStoreCtxCleanup` | `0x60EBE4` | **死代码（无调用者）** |

### 1.2 为什么用不了

**卡在 `SmFirstTimeInit` 的门禁。**

```asm
0x4EA9DF  mov  rax, PspSystemPartition
0x4EA9E6  cmp  [rsi+0x830], rax      ; 是系统分区？
0x4EA9ED  je   0x4EAA02              ; 是 → 放行
0x4EA9EF  cmp  [rsi+0x838], 0        ; 不是 → 看 0x838
0x4EA9F6  jne  0x4EAA02              ; 非 0 → 放行
0x4EA9F8  mov  edi, 0xC00001AE       ; 否则拒绝
```

实测：

| 字段 | 值 | 含义 |
|---|---|---|
| `SM_PARTITION+0x830` | `0xFFFFAA038965F290` | 不是 `PspSystemPartition` |
| `SM_PARTITION+0x838` | `0x0` | **门禁拒绝** |

而 `+0x838` 不是"随便填非 0 就行"的占位字段——它是传给 `PsCreateMinimalProcess` 的**父进程指针**：

```asm
0x4EAA69  mov  rax, [rsi+0x838]       ; 取 0x838
0x4EAA74  mov  r9b, [rdi+0x5FA]
0x4EAA7B  lea  rdx, [rip+0x91E46E]     ; 进程名 "Memory Compression"
0x4EAA97  mov  [rsp+0x40], rax         ; 0x838 作为参数
0x4EAAB3  call PsCreateMinimalProcess  ; 创建最小进程
```

**结论：per-process store 的创建路径在当前系统配置下是关闭的。** 不是参数调错，是内核没给这条路留入口。

## 二、三处早期错误结论的修正

### 2.1 `PspSystemPartition` 与压缩分区的关系

**早期报告（11-03）**：`PspSystemPartition != Memory Compression 的分区对象`，推断压缩用的是独立分区。

**实测（11-04）修正**：

```
PspSystemPartition      = 0xFFFFAA03896EAC60
MemCompr 的 EPROCESS+0x758 = 0xFFFFAA03896EAC60   ← 完全相同
```

两者相同。但要注意指针链有三层：

```
EPROCESS+0x758          = 0xFFFFAA03896EAC60   包装对象
  +0x00                 = 0xFFFFF800B6C38D00   _MI_PARTITION（真正的分区）
  +0x18                 = 0xFFFFAA0389ACF010   SM_PARTITION

MiState+0x3548          = 分区数组
  数组[0]               = 0xFFFFF800B6C38D00   _MI_PARTITION
```

**`EPROCESS+0x758` 拿到的不是 `_MI_PARTITION`，而是包装对象。** 早期报告在这个对象上读 `+0x4BC0`/`+0x4CA0` 得到 0，是因为偏移基准错了。

### 2.2 `SM_PARTITION+0x7D0` 的真实语义

**早期报告**：`+0x7D0` bit `0x20` 是"压缩使能位"。

**实测修正**：`+0x7D0` 存的是 `_MI_PARTITION+0x4BC0` 与 `+0x4CA0` 的差值，实时同步。

```
_MI_PARTITION+0x4BC0 = 64008   可用页列表计数
_MI_PARTITION+0x4CA0 = 63885   保留页计数
差值                  = 123
SM_PARTITION+0x7D0   = 123     ← 完全一致
```

压缩使能位在 **`store+0x00` 的 bit 17（`0x20000`）**，实测 `store+0x00 = 0x320800`，该位已置位。

### 2.3 压缩的真正触发条件

**早期报告**：阈值是"可用页 < 16 页"。

**实测修正**：`_MI_PARTITION+0x4900` 才是**可用物理页数**（实测 2,360,898 页 = 9.01 GB，与系统可用 8.99 GB 吻合）。`+0x4BC0` 只是某个页列表的计数。

压缩条件分级（`MiStoreUpdateMemoryConditions` @ `0x34CF3C`）：

```asm
0x34CF73  rsi = [rdi+0x4900]     ; 可用物理页数
0x34CF96  cmp rsi, 0xA0          ; 160 页
0x34CF9D  jb  等级 0
0x34CFA6  cmp rsi, 0x420         ; 1056 页
0x34CFAD  jb  等级 6
                                 ; >= 1056 → 等级 8（压缩线程优先级 18）
```

**当前系统 2,360,898 页 ≥ 1056，压缩条件已是最高等级。** 压缩不启动不是条件不足，是没有数据可压。

## 三、完整调用方式

### 3.1 定位 Memory Compression 进程

**关键**：EPROCESS 里的映像名是 `MemCompr`（8 字符），**不是**显示名 `Memory Compression`。且该进程**不挂 `ActiveProcessLinks` 链表**，必须走 `PspCidTable`。

```c
// EPROCESS 偏移（实测验证）
#define EPROCESS_PARTITION   0x758

static UINT64 FindMemCompr(void)
{
    int pid;
    PVOID proc;
    NTSTATUS st;
    unsigned char* nm;
    int i;

    // 必须用 PsLookupProcessByProcessId，不能遍历链表
    for (pid = 4; pid < 65536; pid += 4) {
        proc = 0;
        st = PsLookupProcessByProcessId((PVOID)(UINT64)pid, &proc);
        if (st != STATUS_SUCCESS || proc == 0)
            continue;

        nm = PsGetProcessImageFileName(proc);
        if (nm) {
            int match = 1;
            const char* t = "MemCompr";      // 8 字符，注意不是 "Memory Compression"
            for (i = 0; i < 8; i++) {
                if (nm[i] != (unsigned char)t[i]) { match = 0; break; }
            }
            if (match)
                return (UINT64)proc;          // 返回带引用，调用方负责解引用
        }
        ObfDereferenceObject(proc);
    }
    return 0;
}
```

### 3.2 获取内核基址

不需要 `MmGetSystemRoutineAddress` 或导出表，用导入函数的地址反推：

```c
__declspec(dllimport) void DbgPrint(const char* fmt, ...);
extern PVOID __imp_DbgPrint;

#define DBGPRINT_RVA   0x358CB0     // 实测：DbgPrint 在 ntoskrnl 的 RVA

static UINT64 g_NtBase = 0;

static UINT64 GetNtBase(void)
{
    if (!g_NtBase)
        g_NtBase = (UINT64)(*(UINT64*)(&__imp_DbgPrint)) - DBGPRINT_RVA;
    return g_NtBase;
}
```

**验证**：`GetNtBase()` 返回值高 16 位应为 `0xFFFF`，否则拒绝使用。

### 3.3 指针链解析

```c
#define EPROCESS_PARTITION      0x758
#define PARTITION_SM_PART       0x18
#define SM_PART_MANAGER         0x4F0

UINT64 ep      = FindMemCompr();
UINT64 partObj = ReadQ(ep + EPROCESS_PARTITION);      // 包装对象
UINT64 smPart  = ReadQ(partObj + PARTITION_SM_PART);  // SM_PARTITION
UINT64 mgr     = smPart + SM_PART_MANAGER;            // SM_COMPRESS_MANAGER

ObfDereferenceObject((PVOID)ep);   // 用完必须解引用
```

**注意 `SM_PART_MANAGER` 是 `lea`（取地址），不是 `mov`（读值）。**

验证依据（`SmpPageEvict` @ `0x24A6BB`）：

```asm
0x24A6BB  lea  rcx, [rdi + 0x630]    ; 传地址给 SmFpAllocate
0x24A6C2  call SmFpAllocate
```

`SmFpAllocate` 内部用 `[rcx + 0x60 + type*2]` 读大小表：

```
[smPart+0x690] = 0x10 = 16 字节   type 0（IO 上下文）
[smPart+0x692] = 0x28 = 40 字节   type 1（工作项）
```

### 3.4 功能一：设置压缩线程优先级

```c
#define FN_UPDATE_MEMCOND   0x4C0040    // SmCompressManagerUpdateMemoryCondition

// 签名：NTSTATUS fn(SM_COMPRESS_MANAGER* mgr, SMP_MEMORY_CONDITION cond, ULONG flag)
typedef NTSTATUS (*PFN)(PVOID, UINT32, UINT32);

static NTSTATUS HandleSetPriority(PMEMCOMP_SET_PRIORITY in)
{
    UINT64 ep, part, smPart, mgr, fnAddr;

    if (in->Cond > 4) return STATUS_INVALID_PARAM;

    ep = FindMemCompr();
    if (!ep) return STATUS_NOT_SUPPORTED;

    part   = ReadQ(ep + EPROCESS_PARTITION);
    smPart = IsKernelPtr(part) ? ReadQ(part + PARTITION_SM_PART) : 0;
    ObfDereferenceObject((PVOID)ep);

    if (!IsKernelPtr(smPart)) return STATUS_NOT_SUPPORTED;

    mgr = smPart + SM_PART_MANAGER;
    if (!IsKernelPtr(ReadQ(mgr))) return STATUS_NOT_SUPPORTED;

    fnAddr = GetNtBase() + FN_UPDATE_MEMCOND;
    if ((fnAddr >> 48) != 0xFFFF) return STATUS_NOT_SUPPORTED;

    return ((PFN)fnAddr)((PVOID)mgr, in->Cond, in->Flag ? in->Flag : 1);
}
```

**cond 与线程优先级的映射**（`PriorityByMemoryCondition` @ RVA `0x38018`）：

| cond | 线程优先级 |
|---|---|
| 0 | 18（最高） |
| 1 | 18 |
| 2 | 10 |
| 3 | 8 |
| 4 | -1（最低） |

**这是唯一已验证有效、无副作用的控制手段。**

### 3.5 功能二：主动 Trim（效果有限）

```c
#define SIC_STORE   0x6D      // SystemInformationClass
#define SUB_TRIM    0x15      // SmProcessSystemStoreTrimRequest

static NTSTATUS DoTrimRequest(UINT32 flags, UINT64 val8)
{
    UINT32 low = flags & 0xFF;
    UINT32 innerLen = (low == 2) ? 0x18 : 0x10;
    UINT32 inner[8];
    UINT64 outer[3];
    int i;

    for (i = 0; i < 8; i++) inner[i] = 0;
    inner[0] = flags;
    *(UINT64*)((char*)inner + 8) = val8;

    outer[0] = 1;                                    // 固定 1
    *(UINT32*)((char*)outer + 4) = SUB_TRIM;         // ★ 必须是 0x15
    outer[1] = (UINT64)(size_t)inner;                // 内层指针
    outer[2] = innerLen;                             // 内层长度 0x10 或 0x18

    return ZwSetSystemInformation(SIC_STORE, (PVOID)outer, 0x18);
}

static NTSTATUS HandleActiveTrim(PMEMCOMP_ACTIVE_TRIM io)
{
    UINT64 ep, apcState[0x10];
    NTSTATUS trimSt;
    UINT32 flags;

    if (io->Flags > 0xFFFF) return STATUS_INVALID_PARAM;
    flags = io->Flags ? io->Flags : 1;

    ep = FindMemCompr();
    if (!ep) return STATUS_NOT_SUPPORTED;

    // ★ 必须切到 MemCompr 上下文：API 只作用于调用者所在分区
    KeStackAttachProcess((PVOID)ep, (PVOID)apcState);
    trimSt = DoTrimRequest(flags, io->Val8 ? io->Val8 : 1);
    KeUnstackDetachProcess((PVOID)apcState);

    ObfDereferenceObject((PVOID)ep);

    io->Status = trimSt;
    return trimSt;
}
```

**两个关键修正（早期踩过的坑）**：

1. **sub-command 必须是 `0x15`，不是 `0x14`**
   - `0x11` = SmProcessResizeRequest
   - `0x12` = SmcProcessResizeRequest
   - `0x13` = SmProcessConfigRequest
   - `0x14` = SmProcessStoreMemoryPriorityRequest
   - **`0x15` = SmProcessSystemStoreTrimRequest**

2. **必须 `KeStackAttachProcess` 切到 MemCompr 上下文**
   - 否则返回 `STATUS_INVALID_DEVICE_REQUEST (0xC00000BB)`
   - 因为该 API 只作用于调用者所在分区

**注意 `KeStackAttachProcess` 返回 void，不是 NTSTATUS。** RAX 里是垃圾值，不能判断返回值。

### 3.6 功能三：发起页驱逐（异步，效果有限）

```c
#define FN_EVICT_INITIATE   0x2DF8C0    // SmFeEvictInitiate
#define FN_EVICT_COMPLETE   0x3E1840    // MmStoreEvictComplete
#define FN_FP_ALLOCATE      0x317D10    // SmFpAllocate
#define FN_IOCTX_QUEUE      0x317440    // SmIoCtxQueueWork
#define ST_EVICT_PENDING    0x400

// 完整流程（从 SmpPageEvict @ 0x24A5F4 反汇编还原）：
//   1. SmFeEvictInitiate(mgr, &key, &count, &result)
//   2. if (result == 0x400) → MmStoreEvictComplete([mgr+0x830], key, count)
//   3. 否则 → SmFpAllocate 分配 IO 上下文和工作项，填字段，SmIoCtxQueueWork 入队
```

工作项结构（40 字节）：

```
+0x00  dword  type = 1
+0x04  dword  0
+0x08  dword  page key
+0x0C  dword  count
+0x10  qword  0
+0x18  qword  0
+0x20  qword  ioctx
```

**B+ 树根节点**在 `SM_PARTITION+0x1C0`：

```
+0x00  dword  条目数（低 16 位）| 层级（bit 24）
+0x08  qword  条目[0].data
+0x10  dword  条目[0].key        ← 每 16 字节一条
```

**实测结果**：`SmFeEvictInitiate` 返回 `0x400`，`MmStoreEvictComplete` 执行成功，树条目从 3 降到 2，但**压缩进程 WS 无变化**。这是"标记驱逐"，实际释放依赖系统决策。

### 3.7 驱动框架要点

```c
#define DRIVER_UNLOAD        0x68     // ★ 实测验证
#define DRIVER_MAJOR_FUNCS   0x70

#define IRP_SYSTEM_BUFFER    0x18
#define IRP_IO_STATUS        0x30
#define IRP_INFO             0x38
#define IRP_CURRENT_STACK    0xB8
```

**`DriverUnload` 注册必须防止编译器优化**：

```c
// 错误写法：编译器会把整行优化掉
static void ProbeUnload(PVOID DriverObject)
{
    (void)DriverObject;      // 空函数
}
*(void**)((char*)DriverObject + 0x68) = (void*)ProbeUnload;

// 正确写法：Unload 函数必须有实际副作用，注册用 volatile
static void ProbeUnload(PVOID DriverObject)
{
    volatile UINT64* p = (volatile UINT64*)DriverObject;
    if (p) *(volatile UINT64*)((char*)p + 0x68) = 0;   // 清空 Unload 槽
}
*(volatile UINT64*)((char*)DriverObject + 0x68) = (UINT64)(size_t)ProbeUnload;
```

反汇编验证：修正后能看到 `mov qword ptr [rcx + 0x68], rax`。修正前完全没有该指令，导致 `sc stop` 返回 `NOT_STOPPABLE`。

### 3.8 完整编译命令

```bat
@echo off
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat" >nul 2>&1
cd /d C:\Projects\memcomp_build

exit /b 0
:fail
echo === FAILED ===
exit /b 1
```

**四个必须注意的点**：

1. **必须加 `/utf-8`** —— 否则中文注释被 GBK 解析，吞掉换行导致大量语法错误（曾报 25 处）
2. **必须自己实现 `memset`/`memcpy`** —— `/NODEFAULTLIB` 下编译器优化会生成库调用，链接失败
3. **路径不能含中文** —— `cl.exe` 无法访问无短名的中文目录，需用 junction 或纯 ASCII 路径
4. **`/GS- /Gs- /Zl`** —— 禁用缓冲区检查、栈探测、默认库，避免引入 CRT 依赖

### 3.10 IOCTL 协议

```c
#define MEMCOMP_DEVICE_TYPE   0x8000
#define CTL_CODE(d, f, m, a)  (((d) << 16) | ((a) << 14) | ((f) << 2) | (m))

#define FUNC_SET_PRIORITY     0x801
#define FUNC_ACTIVE_TRIM      0x802

// 输入结构
typedef struct _MEMCOMP_SET_PRIORITY {
    unsigned long Cond;      // 0/1=最高18, 2=中10, 3=低8, 4=最低-1
    unsigned long Flag;
} MEMCOMP_SET_PRIORITY;      // 8 字节

typedef struct _MEMCOMP_ACTIVE_TRIM {
    unsigned long      Flags;      // 低字节 1 或 2
    unsigned long      Reserved;
    unsigned long long Val8;       // 内层 [0x08]，必须非零
    long               Status;     // 输出：NTSTATUS
    unsigned long      Reserved2;
    unsigned long      Reserved3;
} MEMCOMP_ACTIVE_TRIM;       // 32 字节
```

## 五、为什么驱动方案全部无效

### 5.1 完整触发链

```
脏页产生
  → 系统判断需要换出（由 _MI_PARTITION+0x4900 可用页数决定）
    → MiWakeModifiedPageWriter 被调用
      → MiModifiedPageWriter 线程醒来
        → MiGatherPagefilePages 收集页面
          → MiStoreWriteModifiedPages
            → SmPageWrite
              → SmFeAddInitiate
                → 页被压缩进 store
```

### 5.2 每一环都依赖上一环的"实际需求"

驱动能做的只有：
- 调优先级（有效，但不产生压缩数据）
- 唤醒线程（成功，但线程醒来无事可做）
- 标记驱逐（成功，但释放依赖系统决策）

**驱动无法制造"页面必须换出"这个需求。** 这是内存管理器的内部决策，由可用物理页数驱动。

### 5.3 数据证明

```
调用 MiWakeModifiedPageWriter 前: 可用页 2,353,741
调用 MiWakeModifiedPageWriter 后: 可用页 2,353,741    ← 完全相同
```

## 七、结论

### 7.1 单进程压缩：不可行

**架构支持，门禁关闭。**

`SmFirstTimeInit` 要求分区要么是系统分区（`+0x830 == PspSystemPartition`），要么提供父进程指针（`+0x838 != 0`）。当前系统两者都不满足，且 `+0x838` 的语义是 `PsCreateMinimalProcess` 的父进程，无法伪造。

**即使强行绕过门禁**，后续会调用 `PsCreateMinimalProcess` 创建真实进程，无法提供正确的父进程语义。

### 7.2 全局主动压缩：不可行

**Windows 的压缩是被动机制。**

压缩发生在"页面必须换出"时，先尝试压缩、失败才写盘。这个决策由可用物理页数驱动，外部无法制造。

已验证的所有内部函数（`SmStTrimWsStore`、`SmFeEvictInitiate`、`MiWakeModifiedPageWriter`）都返回成功但零效果。

### 7.3 可行替代：工作集修剪

**这是唯一真正有效的方法。**

`EmptyWorkingSet` 把进程工作集页面推入 Modified 列表，制造真实的换出需求，进而触发压缩。

实测：38 个后台进程释放 1,694.8 MB，压缩进程 WS 从 590 MB 增至 839 MB。

**这不是"主动压缩"，但能达到"让内存被压缩回收"的实际效果。**

## 九、一句话总结

**Windows 内核确实有 per-process 压缩存储的完整代码，但 `SmFirstTimeInit` 的门禁在当前系统配置下永久关闭；而全局压缩是纯被动机制，所有内部函数都能调用成功却不产生任何效果。唯一真正能触发压缩的是制造真实的换出需求——这只能用 `EmptyWorkingSet` 从用户态做到。**
